# 架构

locoSaonduh 把一台设备正在播放的声音采集下来，经局域网实时送到其他设备。接收端可以把多路声音混成一路，用一个耳机或音响播放。

它是原生桌面程序，不是文件传输器，也不是云端服务。

## 技术栈

| 层 | 选择 | 原因 |
| --- | --- | --- |
| UI | Tauri 2 + Svelte 5 | Rust 核心、系统 WebView、低于 Flutter 的体积与内存 |
| 音频 I/O | cpal 0.18 | 桌面端统一设备接口；Windows 上通过 WASAPI 回环采集输出端点 |
| 编解码 | opus-pure 0.2 | 纯 Rust Opus，无 C 工具链、无 GC、10 ms 帧 |
| 传输 | 自有 UDP 协议 | 局域网直连、不需要证书交换，适合单向实时媒体 |
| 发现 | UDP 组播 + 定向广播 + 子网扫描 | 不依赖 mDNS 服务，并能绕过 VPN 抢占的默认路由 |
| 线程通信 | rtrb | 音频回调中使用的无锁环形缓冲 |

## 数据路径

发送端：

```text
系统输出 / 麦克风
        │  cpal 回调，实时线程
        ▼
  rtrb 环形缓冲（f32）
        │
        ▼
采样率转换 + 声道归并（48 kHz / 2 ch）
        │
        ▼
Opus 编码，10 ms 帧
        │
        ▼
当前帧 + 前一帧打包进一个 UDP 数据报
        │
        ▼
每个订阅者（同一编码，最多 24 个听众）
```

接收端：

```text
UDP 数据报
        │
        ▼
按发送端 / session 分流
        │
        ▼
自适应抖动缓冲（去重、重排、丢包检测）
        │
        ▼
Opus 解码 / PLC
        │
        ▼
多路 PCM 求和 + 增益归一
        │
        ▼
rtrb → cpal 输出回调（48 kHz 转设备采样率）
```

音频回调只做少量样本搬运和原子量更新。Opus、重采样和混音都在非实时线程中完成。

## 发现与控制

所有节点监听同一个 UDP 端口，默认 `53410`。

- 组播组：`239.255.77.77:53410`
- 每个已连接网卡分别发送组播、受限广播 `255.255.255.255` 和定向广播（例如 `192.168.10.255`）
- 每 12 秒对每个网卡的 /24 可用地址做一次单播 `probe` 扫描；大网段会限制在本地 /24 与最多 1024 个地址内
- 启动时发送完整 `probe`，扫描目标收到后立即单播回应自己的 `announce`
- 每 2 秒发送 `announce`；已知节点还会收到单播通告；25 秒未见的节点从列表移除

发现报文是 JSON，音频报文是固定头二进制。两者共用端口，以开头魔数区分。

发送发现包时会创建绑定到具体网卡地址的临时 UDP socket，而不是只依赖路由表。Windows 上 VPN / FlClash / 虚拟网卡经常拥有默认路由；如果直接用监听 socket 发送 `255.255.255.255`，报文会从 `198.18.x.x` 这样的隧道地址发出，物理 Wi-Fi 上的对端永远收不到。绑定源地址后，受限广播、定向广播和组播都会从真实网卡发出。

单播扫描从主监听 socket 发出，因此 v0.1.0 的旧节点也能把回应发回 `53410`。新节点在 `probe` 中携带完整 `announce`，收到探测时双方都会立即建立对端记录，不再依赖广播能否到达。设置页还提供手动 IP 探测，用于跨 VLAN 或扫描不到的网络。

控制消息：

- `announce`：设备名、平台、广播状态、session、音源、监听人数
- `probe` / 单播 `announce`：立即刷新附近设备
- `subscribe` / `subscribed`：接收端请求加入，发送端回应 session 与编码参数
- `unsubscribe` / `ended`：退出与结束
- `feedback`：接收端每 500 ms 上报收包、抖动、缓冲、隐藏帧与链路稳定度

接入不设 PIN。发送端在广播期间接受局域网内的订阅请求；这是有意的低摩擦局域网模型，不是互联网安全边界。

## 音频数据报

固定 28 字节头：

| 偏移 | 字段 |
| --- | --- |
| 0 | 魔数 `LSAu` |
| 4 | 协议版本 |
| 5 | 包类型 |
| 7 | 头长度 |
| 8 | session |
| 12 | 序号 |
| 16 | 时间戳（48 kHz 样本数） |
| 20 | 当前帧长度 |
| 22 | 前一帧长度 |
| 24 | 当前码率（kbps） |

载荷是当前 Opus 帧，紧接着前一帧。

每个数据报都带上一帧，意味着单个 UDP 丢包不会制造音频空洞。它用约 2 倍的包体换取低延迟的 1 丢包保护，不需要 NACK 往返。连续丢包仍然会进入 PLC，再严重时暂停并重新建立缓冲。

## 自动权衡

系统没有“音质 / 延迟”滑块，默认只有自动。目标是在当前链路条件下同时保持连续、尽量低的延迟和足够的清晰度。

接收端：

- 播放缓冲目标范围 30–120 ms
- 起始 30 ms；抖动估计可把预缓冲提高到最多 60 ms
- 每出现一次实际 concealment，目标增加 20 ms
- 连续 3 帧无法补齐时暂停播放，等缓冲重新填满
- 连续 4 秒无缺口后，目标每次降低 10 ms
- 缓冲积压超过目标 60 ms 时，逐步丢弃最老帧，防止延迟永久漂移

发送端：

- 目标码率 64 / 80 / 112 / 160 kbps，默认 112 kbps
- 以最差听众的反馈决定共享码率；链路干净且稳定时才升到 160 kbps
- 丢包或抖动升高时优先降码率
- 码率每次最多变化 16–24 kbps，避免编码器与听觉上的突变
- Opus 帧长固定 10 ms，不通过加长帧换带宽

界面展示真实的当前码率、抖动、丢包、缓冲和输出延迟，不展示虚构的评分。

## 并发模型

- **cpal 回调**：采集回调把 f32 样本写入 rtrb；播放回调从 rtrb 取样本。
- **编码线程**：每个发送会话一个，读取采集环形缓冲，重采样、编码、打包、发送。
- **会话线程**：非阻塞读取 UDP，处理发现、订阅、反馈和 Tauri 命令；每轮处理后让出 2 ms。
- **混音线程**：每 10 ms 产生一个立体声块，维护每个来源的抖动缓冲和解码器。
- **UI 线程**：每 180 ms 收到一份状态快照。

会话线程此前是一个容易踩的坑：阻塞式 `recv_from` 在持续音频下会一直等到下一包，导致状态发布和反馈饥饿。现在收包是非阻塞的，每轮最多处理 96 个数据报后让出。

## 为什么不是 WebTransport

WebTransport 适合浏览器接收端，但会带来 TLS 证书信任、HTTP/3 服务、浏览器自动播放策略和额外封装。当前版本的目标是原生节点之间的单向媒体，不需要这些能力。

在原生对原生、可信局域网的前提下，直接用 UDP + Opus + 帧冗余更短、更可控，也更容易在 Windows 上做到低延迟回环采集。如果以后把“浏览器免安装收听”作为核心需求，WebTransport 会是合理的新增路径，而不是替换现有原生链路的前提。

## 已知边界

- 不加密，不认证，只适合可信局域网，不应暴露到公网。
- 多路混音不做采样级时钟同步；每一路独立缓冲，设备时钟漂移由缓冲与输出重采样吸收。
- 不提供每路音量、静音或单独延迟控制。
- Windows 的系统回环已验证。macOS 依赖 CoreAudio 的系统回环能力；Linux 的系统输出通常需要选择 monitor 输入设备。
- 没有房间、账号、云端目录或远程穿透。
